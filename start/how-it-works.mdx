---
title: 'How It Works'
---

This page walks through the normal Suncode flow from a fresh AI session to an
archived task. It focuses on runtime behavior: which files are read, which files
are written, which hooks run, and where platform behavior differs.

> This is the day-to-day usage flow. For module boundaries, customization
> points, and implementation details, see [Architecture Overview](/advanced/architecture).

## 1. A session opens

A Suncode project is a repository with `.suncode/` plus one or more platform
directories such as `.claude/`, `.codex/`, `.cursor/`, `.opencode/`,
`.engineer/`, `.kiro/`, or `.pi/`.

On platforms with a SessionStart path, Suncode injects a compact startup
payload. It is an index and state report, not a full dump of every workflow,
spec, or task artifact.

Typical startup context includes:

| Context             | Source                                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Developer identity  | `.suncode/.developer`                                                                                                   |
| Git state           | current branch, dirty files, recent commits                                                                             |
| Active task pointer | `.suncode/.runtime/sessions/<session-key>.json`, with a single-session fallback when exactly one runtime session exists |
| Active task list    | `.suncode/tasks/*/task.json`                                                                                            |
| Workflow index      | compact Phase Index from `.suncode/workflow.md`                                                                         |
| Spec index paths    | `.suncode/spec/**/index.md` paths                                                                                       |
| Workspace memory    | `.suncode/workspace/<developer>/index.md` and recent journal notes                                                      |

The delivery path depends on the platform:

| Platform group                                                                         | Startup behavior                                                                                                                                                      |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code, Cursor, OpenCode, Engineer, Gemini CLI, Qoder, CodeBuddy, Droid, Pi, Trae | A SessionStart hook, plugin, or extension injects compact startup context automatically.                                                                              |
| Codex                                                                                  | `AGENTS.md` loads automatically. Suncode installs a `UserPromptSubmit` hook; on no-task turns it can inject a `<suncode-bootstrap>` reminder to read `suncode-start`. |
| Copilot                                                                                | SessionStart output is diagnostic-only in current Copilot hosts. Suncode relies on prompt hooks and skill files for model-visible context.                            |
| Kiro                                                                                   | Suncode content is delivered through `.kiro/` skills and agent files; there is no Suncode SessionStart hook by default.                                               |
| Kilo, Antigravity, Devin                                                               | The main session reads a workflow or skill entry explicitly.                                                                                                          |

After this step, the AI should know where Suncode context lives. Detailed phase
instructions are loaded on demand through workflow-state breadcrumbs, skills, or
`get_context.py`.

## 2. Each prompt gets the current workflow state

On hook-capable platforms, every user message triggers a lightweight
workflow-state injection. This is the per-turn guardrail that keeps the main
session aligned with the current task status.

The hook resolves the active task for the current session:

```text
cwd
  -> find .suncode/
  -> resolve session key
  -> read .suncode/.runtime/sessions/<session-key>.json
  -> read .suncode/tasks/<task>/task.json
  -> read task.json.status
```

Then it parses `.suncode/workflow.md` for the matching block:

```text
[workflow-state:STATUS]
...
[/workflow-state:STATUS]
```

The block body is wrapped in `<workflow-state>...</workflow-state>` and injected
into the current turn. SessionStart workflow summaries use the
`<suncode-workflow>` tag.

Important details:

- The hook is parser-only. Breadcrumb wording lives in `.suncode/workflow.md`.
- Python and JavaScript hooks do not carry duplicated fallback dictionaries.
- If no active task exists, the pseudo-status is `no_task`.
- If a matching block is missing, the hook emits `Refer to workflow.md for current step.`
- Codex also receives a `<codex-mode>` banner when `codex.dispatch_mode` changes implementation routing.

Changing workflow-state behavior starts with `.suncode/workflow.md`, not the
hook script.

## 3. Suncode triages the current turn

When there is no active task, the AI first classifies the current turn and asks
for task-creation consent before creating anything under `.suncode/tasks/`.

| Route               | When it applies                                                                    | What the AI asks                                                                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Simple conversation | No repo writes; simple Q&A, explanation, lookup, or discussion                     | No task by default. If a task might help, ask only whether this turn should create a Suncode task.                                                        |
| Inline small task   | A small contained edit that can be understood and verified in the current turn     | Ask only whether this turn should create a Suncode task. If the user says no, skip Suncode for this turn and continue inline.                             |
| Full Suncode task   | Multi-file work, workflow/spec/platform changes, template generation, durable plan | Explain why a task is useful and ask whether Suncode may create a task and enter planning. If the user says no, clarify scope or suggest a smaller split. |

User consent to create a task is not consent to start implementation. Starting
implementation has a separate planning review gate.

## 4. Task creation writes the planning state

When the user consents, the main session creates a task:

```bash
python3 ./.suncode/scripts/task.py create "<title>" --slug <name>
```

This command writes a task directory:

```text
.suncode/tasks/<MM-DD-name>/
├── task.json
├── prd.md
├── implement.jsonl
└── check.jsonl
```

`prd.md` is always created from the default template. `implement.jsonl` and
`check.jsonl` may be seeded for sub-agent-capable platforms. `design.md` and
`implement.md` are not created by the script; the AI writes them during planning
when the task is complex enough to need them.

The initial `task.json` status is `planning`. `task.py create` also best-effort
sets the current session's active-task pointer, so the next prompt can receive
the `[workflow-state:planning]` block without waiting for `task.py start`. New
tasks also snapshot the current execution-DAG policy under
`task.json.meta.execution`; changing project configuration later therefore does
not retroactively make an existing complex task stricter.

## 5. Planning writes the right artifacts

Planning converts the request into files that implementation and review can
trust.

| Artifact          | Required when                          | Purpose                                                                                          |
| ----------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `prd.md`          | every task                             | Requirements, constraints, acceptance criteria, and out-of-scope items.                          |
| `design.md`       | complex tasks                          | Technical design: boundaries, contracts, data flow, compatibility, tradeoffs, rollback.          |
| `implement.md`    | complex tasks                          | Human-readable ordered checklist, validation commands, review gates, and legacy serial fallback. |
| `execution.json`  | when `execution.dag.enabled`           | Canonical versioned dependency graph shared by inline, native sub-agent, and channel executors.  |
| `research/*.md`   | when investigation matters             | Durable facts discovered during planning.                                                        |
| `implement.jsonl` | when stable implementation input helps | Spec/research sources that a node context may include.                                           |
| `check.jsonl`     | when stable verification input helps   | Spec/research sources that a verification node context may include.                              |

These files have separate responsibilities. `implement.md` is the human and
legacy serial view. `execution.json` is the execution source of truth. The
JSONL files are reusable source lists, not schedulers.

Human documentation for a lightweight task can remain PRD-only, but a DAG-enabled
task still receives a reviewed one-node `execution.json` before implementation.
Complex tasks need `prd.md`, `design.md`, `implement.md`, and a real dependency
graph whose branches converge on a final integration/check barrier. Do not turn
independent work into a serial chain merely because it appears later in the
checklist.

Every complex `implement.md` should include a parseable implementation checklist:

```md
## 实施清单

- [ ] [P1] Subtask name: Subtask description
- [ ] [P2] Subtask name: Subtask description
```

For Hub display, Suncode prefers an explicit `subtasks.json` v1 override, then a
stable projection of `execution.json`, then this checklist. `subtasks.json` is
display data, never the execution graph.

## 6. Context manifests stay narrow

`implement.jsonl` and `check.jsonl` list stable context files to read before
implementation or review.

```jsonl
{"file": ".suncode/spec/docs-site/docs/style-guide.md", "reason": "Docs writing style"}
{"file": ".suncode/tasks/04-30-example/research/platforms.md", "reason": "Platform behavior research"}
```

Rules:

- Include spec files and task research files.
- Do not list source files that are about to be modified.
- Do not leave only the seed `_example` row when a sub-agent needs context.
- Put implementation-writing context in `implement.jsonl`.
- Put verification and quality context in `check.jsonl`.

Before a DAG node is claimed, Suncode builds an immutable, bounded context
package under `.suncode/.runtime/execution/`. Its manifest records the node
contract, read/write/resource boundaries, selected sources, direct succeeded
dependency results, byte budgets, truncation/redaction decisions, and SHA-256
hashes. The dispatch prompt points at this manifest; it does not copy the main
conversation transcript. Codex dispatches with `fork_turns = "none"`, and
channel workers receive the manifest and rendered content as context files.

Inline consumes the same node manifest and the same dependency graph. Its only
scheduling difference is `maxConcurrency = 1`.

## 7. Activation enters implementation

After artifact review, Suncode activates the task:

```bash
python3 ./.suncode/scripts/task.py execution validate <task-dir>
python3 ./.suncode/scripts/task.py start <task-dir>
```

This changes `task.json.status` from `planning` to `in_progress`. When the DAG
feature is enabled, a malformed explicit plan always blocks activation. A new
complex task also requires the plan when its creation-time policy snapshot has
`requireForComplexTasks: true`; older tasks remain compatible.

For Hub-bound tasks, run `suncode hub plan-ready --task current` before
`task.py start`. Standard and change tasks run Hub start preflight; quick tasks
upload available plan artifacts but skip Hub start preflight and plan approval.

On the next prompt, the workflow-state hook injects the matching
`[workflow-state:in_progress]` block. That block covers implementation, check,
spec update, commit planning, and finish-work routing.

## 8. Implementation reads task artifacts and specs

Execution starts by freezing the reviewed plan hash:

```bash
python3 ./.suncode/scripts/task.py execution start-run <task-dir> --executor native-subagent
python3 ./.suncode/scripts/task.py execution ready <task-dir> --run-id <run-id>
```

The coordinator claims every conflict-free ready node selected for the current
capacity and dispatches all of them before waiting. It records the first returned
`NodeResult` v1, immediately recomputes the ready set, and continues until the
final barrier succeeds. Read/write glob overlap, resource locks, unsupported
roles, and shared global lock files prevent unsafe concurrency. Runtime state,
events, attempts, results, and contexts are persisted so orphaned work can be
recovered without trusting transcript text.

Codex can run in two modes:

| Mode        | Meaning                                                                                                                     |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- |
| `inline`    | The main session executes the same DAG one ready node at a time (`maxConcurrency = 1`).                                     |
| `sub-agent` | The main session coordinates the DAG and fans out safe ready nodes; each worker receives only its claimed context manifest. |

## 9. Check reviews and self-fixes

After implementation, Suncode runs `suncode-check`.

The check path reads:

- `prd.md`
- `design.md` if present
- `implement.md` if present
- `check.jsonl` entries when present
- relevant specs and research
- the changed files
- local test, lint, type-check, or format commands

In a DAG, check nodes are read-only reporters so parallel verification cannot
race on the shared worktree. When a finding needs a write, the graph routes it
to one explicit fix node and then reruns the affected checks. The legacy direct
`suncode-check` skill can still self-fix in a bounded loop outside DAG dispatch.

## 10. Finish updates durable knowledge

After checks pass, the main session performs final verification and loads
`suncode-update-spec`.

This step asks whether the task taught a reusable rule. If yes, the rule is
written into `.suncode/spec/` so future tasks can load it through JSONL or direct
skill context.

Task-local facts stay in `.suncode/tasks/<task>/`; stable team rules move to
`.suncode/spec/`.

## 11. The main session drives the work commit

The commit boundary is separate from implementation and separate from
`/suncode:finish-work`.

In Phase 3.4, the main session:

1. Reads `git status --porcelain`.
2. Separates files changed in this task from unrelated dirty files.
3. Groups task files into logical commits.
4. Prints the proposed commit plan.
5. Waits for one user confirmation.
6. Runs `git add` and `git commit` for the approved batches.

For docs-site changes, there is often a submodule boundary:

1. Commit inside `docs-site/`.
2. Return to the parent repository.
3. Commit the updated `docs-site` submodule pointer.

## 12. `/suncode:finish-work` archives and journals

Only after the work commit exists should `/suncode:finish-work` run.

`/suncode:finish-work` does bookkeeping:

- classifies dirty paths and stops if current-task work is still uncommitted
- archives the task under `.suncode/tasks/archive/YYYY-MM/`
- appends the session summary to `.suncode/workspace/<developer>/journal-N.md`
- updates workspace indexes

It is not the command that commits feature code.

## What survives the session

After the flow completes, durable state lives in files:

| Stored in                         | What survives                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------- |
| `.suncode/tasks/<task>/`          | PRD, design, implementation plan, research, context manifests, metadata, and archived history. |
| `.suncode/spec/`                  | Team conventions and reusable lessons.                                                         |
| `.suncode/workspace/<developer>/` | Developer journals and cross-session notes.                                                    |
| Git commits                       | Reviewable units of code, docs, spec, archive, and journal changes.                            |

The next AI session reads the repository state again. It does not need the
previous chat transcript to know what the task was, what specs apply, or what
workflow step comes next.
